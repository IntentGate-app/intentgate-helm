Routing & securing agents

Two halves of one job: point your agents at the gateway, and lock the tool server so they can't go around it. Both are needed — routing without locking leaves an open back door; locking without routing just breaks the agent.

How routing works

Instead of calling the tool server directly, the agent calls the gateway at /v1/mcp with a capability token. The gateway runs the four checks (capability, intent, policy, budget), writes the decision to the audit log, and — if allowed — forwards the call to the real tool server (INTENTGATE_UPSTREAM_URL). The agent only ever knows the gateway's address.

1Mint a token for the agent

Each agent gets its own capability token (this is what the policy and audit are keyed on). Mint it in the console — Tokens, or inline on the Setup → Route step / the agent's Set up button — or via the admin API:

# returns a token like igtok_…
curl -s -X POST "$GATEWAY/v1/admin/mint" \
  -H "Authorization: Bearer $INTENTGATE_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"subject":"refund-bot-01","tools":["issue_refund","read_invoice"]}'

Give every agent a distinct token — never share one across agents, or you lose per-agent policy and attribution.

2Point the agent at the gateway

Pick the pattern by how much of the agent you can change. All four send the same thing: requests to the gateway URL with the token.

A · You build the agent — use the SDK

# pip install intentgate   (or npm i @intentgate-app/intentgate)
from intentgate import Gateway

gw = Gateway(url="https://gateway.your-company.internal:8080", token="igtok_…")
result = gw.call("issue_refund", {"invoice_id": 42, "amount_eur": 50})
# every tool call now goes through the gateway + policy

B · The agent speaks MCP — repoint the MCP client

{
  "mcpServers": {
    "tools": {
      "url": "https://gateway.your-company.internal:8080/v1/mcp",
      "headers": { "Authorization": "Bearer igtok_…" }
    }
  }
}

C · You can edit its config but not its code — swap the URL

# Before — agent calls the tool server directly:
MCP_SERVER_URL=http://toolserver.corp:8090

# After — agent calls the gateway, which forwards to the tool:
MCP_SERVER_URL=https://gateway.your-company.internal:8080/v1/mcp
MCP_AUTH_HEADER="Authorization: Bearer igtok_…"
# no code change — one config value + the token

D · You can't touch the agent at all — redirect at the network

# Point the tool's hostname at the GATEWAY; the gateway's
# INTENTGATE_UPSTREAM_URL points to the tool's REAL address.
DNS:  toolserver.corp.  A  <gateway-ip>
Caveat. With INTENTGATE_REQUIRE_CAPABILITY=true the agent still needs a token, so this path also needs a token-injecting egress proxy in front. If you can edit the agent's config at all, prefer pattern C — it's cleaner.

3Secure it — stop the agent bypassing the gateway

★ The most important step. Routing the agent to the gateway means nothing if it can still reach the tool server directly. Restrict the tool server to accept traffic only from the gateway. Pick the one matching your environment (the console's Setup → Secure step generates these):

Host firewall / cloud security group

# On the tool-server host — accept its port ONLY from the gateway:
iptables -A INPUT -p tcp --dport 8090 -s <gateway-ip> -j ACCEPT
iptables -A INPUT -p tcp --dport 8090 -j DROP            # everyone else
# AWS: tool-server security group inbound —
#   Custom TCP 8090, Source: <gateway-security-group-id> (only)

Kubernetes (NetworkPolicy)

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: tools-only-from-gateway }
spec:
  podSelector: { matchLabels: { app: toolserver } }
  policyTypes: [ Ingress ]
  ingress:
    - from:
        - podSelector: { matchLabels: { app: intentgate-gateway } }
      ports: [ { protocol: TCP, port: 8090 } ]
# default-deny all other ingress to the tool pods

Service mesh (Istio — identity, not just network)

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata: { name: tools-only-gateway }
spec:
  selector: { matchLabels: { app: toolserver } }
  action: ALLOW
  rules:
    - from: [ { source: { principals:
        ["cluster.local/ns/intentgate/sa/intentgate-gateway"] } } ]
# pair with PeerAuthentication mtls: STRICT for cryptographic identity
Why this carries the weight. Today bypass-prevention is network/identity-layer — the gateway does not yet inject the upstream credential, so this segmentation is what guarantees the gateway is the only door to the tools.

4Verify both halves

# 1. Through the gateway with a token → allowed (and audited):
curl -s -X POST "$GATEWAY/v1/mcp" \
  -H "Authorization: Bearer igtok_…" \
  -d '{"tool":"read_invoice","args":{"invoice_id":42}}'      # → result

# 2. Directly to the tool server from a non-gateway host → REFUSED:
curl -m 5 http://toolserver.corp:8090/...                     # → connection refused/timeout

If call 1 succeeds and call 2 is refused, the agent is both routed and contained. That's a governed agent.
