Resiliency & High Availability

How to run IntentGate so that no single failure stops enforcement: multiple gateways behind a load balancer, a shared Redis for budgets, and managed PostgreSQL. This is the production companion to the single-node install guide.

You provide set up & owned by your team  ·  In the box ships with IntentGate

When you need this

A single host is the right choice for a pilot — simple, one of everything. You move to this design for production, where one crash, restart, or deploy must never take enforcement offline. The gateway sits in the request path between your agents and your tools, so if it stops, agents stop. High availability removes that single point of failure.

The architecture

Three changes turn the single-node stack into a highly-available one: run several gateways behind a load balancer, give them a shared Redis so budgets stay consistent, and move to managed PostgreSQL with failover. The console stays a single instance — it is off the request path, so it is not part of the availability story for enforcement.

1The gateways

Run two or more gateway replicas. Each one is stateless on the request path — it loads policy into memory, makes its decision in-process, streams audit out, and keeps no per-request session. That is what makes horizontal scaling safe: any replica can serve any request, so adding copies increases throughput and removes the single point of failure, with no coordination between them on the hot path.

Every replica runs the same configuration — same upstream, same database URL, same Redis URL. You scale by changing a replica count, nothing else.

Health. Each replica serves GET /healthz (HTTP 200 when ready). The load balancer uses this to decide which replicas receive traffic.

You provide the orchestration (Kubernetes replica count, or Compose scale). In the box the gateway image and its stateless design.

2The load balancer

Who owns it. You do. The load balancer is part of your infrastructure — your cloud load balancer (AWS ALB/NLB, Google Cloud Load Balancing, Azure Load Balancer), or a reverse proxy you run (NGINX, HAProxy, Traefik), or, on Kubernetes, a Service plus Ingress. IntentGate does not provide your production load balancer. The HA bundle includes a small NGINX load balancer purely so you can run and test the topology on one host (nginx-lb.conf); it is a reference, not a production component.

How it works

The load balancer is the single address your agents call — it is what INTENTGATE_PUBLIC_GATEWAY_URL points at. It receives each agent request and forwards it to one of the healthy gateway replicas. When a replica fails its health check, the load balancer stops sending it traffic; when it recovers, traffic resumes. Agents only ever know the one load-balancer address, never the individual replicas.

What to configure

SettingValueWhy
Backend poolthe gateway replicas, port 8080The targets traffic is spread across.
Algorithmround-robin or least-connectionsEither is fine — the gateway is stateless, so any replica can serve any request.
Session affinityoff (no sticky sessions)Important: do not pin a client to a replica. There is no session state to preserve, and stickiness only unbalances load and slows failover.
Health checkHTTP GET /healthz, expect 200; interval ~10s; eject after 2–3 failuresThis is how a dead or restarting replica is removed from rotation automatically.
TLSterminate HTTPS at the LB with your certificateAgents call https://gateway…; the LB decrypts and forwards to replicas over your trusted internal network. (TLS pass-through is also fine if you prefer the gateway to terminate.)
Timeoutsconnect ~5s; read timeout ≥ your slowest upstream toolThe gateway forwards to your tool server, so the read timeout must allow for that tool's latency.
Retry / failoverretry the next replica on connection error or 502/503/504So a replica dying mid-request doesn't fail the agent's call — it's retried on a healthy one.
Forwarded headersset X-Forwarded-For / X-Real-IPAuth is token-based, but the real client IP is useful in audit and logs.
The bundled reference. nginx-lb.conf implements exactly this — round-robin across replicas via the container DNS, per-request resolution so scaling needs no proxy restart, a /healthz-aware backend, and proxy_next_upstream retry. Read it as a worked example, then reproduce the same settings on your real load balancer.

You provide the production load balancer and its TLS certificate. In the box a working NGINX reference for testing.

3Redis (shared budget)

What it does. Redis holds the gateway's budget counters — the running totals behind per-agent spend limits and rate limits. Nothing else. It is not a cache for policy or audit; it is the one piece of state the replicas must agree on.

DeploymentRedis?Why
Single gatewayNot usedOne process is already one source of truth, so counters live in memory. Adding Redis would change nothing. The single-node bundle ships no Redis.
Multiple gatewaysRequiredEach replica would otherwise keep its own counters, so a "€10k/day" limit becomes "€10k × replica count." One shared Redis makes all replicas increment one atomic counter, so the limit holds across the fleet.

You turn it on by setting INTENTGATE_REDIS_URL on every gateway replica. The gateway validates the connection at startup, so a wrong URL fails fast rather than silently falling back.

Who owns it. Same model as the database. In the box the HA bundle includes a single Redis container so you can test the topology on one host — but a lone Redis is itself a single point of failure. For production you provide a managed / highly-available Redis (with failover), point INTENTGATE_REDIS_URL at it, and delete the bundled container.

4PostgreSQL (managed)

Policies, audit, and inventory live in PostgreSQL. For HA, replace the bundled single instance with your own managed PostgreSQL with failover (RDS, Cloud SQL, Patroni, etc.) and point the gateways and console at it.

Why it's not the weak link. Enforcement does not read the database on the request path — policy is in memory and audit is streamed out. So a database interruption degrades management and reporting, not protection: the gateways keep deciding allow/deny while Postgres is briefly unavailable.

You provide managed PostgreSQL. Point every gateway and the console at it via INTENTGATE_POSTGRES_URL / SCIM_DATABASE_URL.

5The console

The console is the management UI. It is off the request path, so it is not part of enforcement availability: if it restarts or is down, agents keep calling and the gateways keep enforcing — you simply can't change settings until it returns. One instance is fine; run two behind the load balancer only if you want the UI itself to be highly available.

Failure modes

What failsWhat happens
One gateway replicaThe load balancer's health check ejects it; the others carry the traffic. No impact with ≥2 replicas.
All gateway replicasAgents cannot reach the tools at all — fail-closed. No ungoverned calls slip through; the fix is enough replicas, not fail-open.
The load balancerUse a managed cloud LB (already redundant) or run the proxy in two zones. This is why a single bundled NGINX is test-only.
RedisBudget enforcement is affected; use managed Redis with failover. Other checks (capability, intent, policy) are unaffected.
PostgreSQLManagement & reporting pause; enforcement continues (policy in memory, audit buffered to the stream).
The consoleNo effect on enforcement; you lose the management UI until it's back.

Scaling up or down

Because the gateway is stateless, scaling is a single number.

# Docker Compose (HA bundle)
docker compose -f docker-compose.ha.yml up -d --scale gateway=4

# Kubernetes (Helm chart)
helm upgrade intentgate ./intentgate --set gateway.replicas=4

New replicas register with the load balancer's health check and start taking traffic; removed ones drain as their health check stops passing. No coordination, no migration.

HA readiness checklist

Production high-availability

  • Two or more gateway replicas, all with identical configuration
  • A load balancer you own, fronting the replicas — round-robin, no session affinity, /healthz health check, retry on failure
  • TLS terminated at the load balancer with a valid certificate
  • INTENTGATE_REDIS_URL set on every replica, pointing at managed Redis with failover
  • Managed PostgreSQL with failover, referenced by every gateway and the console
  • Agents configured with the load-balancer address, never an individual replica
  • Failure drill done: kill one replica, confirm traffic continues
