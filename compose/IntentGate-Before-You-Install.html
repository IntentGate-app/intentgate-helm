IntentGate · Installation

Environment prerequisites

What to have in place before installing IntentGate. Prepare the items below, work through the checklists, and the install itself is three commands.

How IntentGate fits

IntentGate acts as a security checkpoint between your AI agents and the tools they use. Every tool call an agent makes passes through the gateway, which checks it against your policies, allows or denies it, and records what happened. Standing that checkpoint up requires a few things in your environment: a host for it to run on, a network position where it is the only route to your tools, a way for staff to sign in, and links to the systems it works alongside. Each one is covered below, with what it is, why it’s needed, and who provides it.

You provide set up by your team  ·  In the box ships with IntentGate  ·  From IntentGate supplied to you

1Host and container runtime

What it is. One Linux host to run IntentGate on. For a pilot, a modest instance is sufficient — roughly 4 vCPU, 8 GB RAM, 20 GB disk. IntentGate is distributed as four containers (gateway, intent extractor, database, console), so the host needs Docker Engine and Docker Compose v2 to run them.

Why it’s needed. This is where IntentGate runs. The four containers are orchestrated together by Compose from a single configuration file.

You provide the host and Docker. In the box the four containers.

2Network placement and segmentation

What it is. The host has to be positioned correctly in your network, and traffic to the protected tools has to be restricted to the gateway. Three conditions:

Agents → gateway
your agents must be able to reach the host on port 8080 to send their tool calls.
Gateway → tools
the host must be able to reach your tool / MCP server to forward approved calls.
Segmentation
a firewall / security-group rule so the tool server accepts traffic only from the gateway, not directly from agents or other clients.

The gateway is the checkpoint on the approved route to your tools. If any other route to the tool server is left open, traffic can detour around the checkpoint — which is why the segmentation rule matters as much as the gateway itself.

Why it’s needed. Enforcement integrity depends on the gateway being the only path to the tools. If agents can reach the tool server directly, they can bypass IntentGate and policy is no longer guaranteed. The firewall rule closes that path. This is the single most important prerequisite.

You provide the network routes and firewall rules (network / security team).

3Image access, DNS, and TLS

Image access

The container images are published to a registry (ghcr.io). The host needs outbound access to it — or to an internal mirror — to pull them once. IntentGate supplies a registry token for authentication.

DNS

Assign internal hostnames for the gateway and the console, for example gateway.your-company.internal and console.your-company.internal, so agents and operators can reach them by name.

TLS

Terminate HTTPS in front of the console (and the gateway) using your standard reverse proxy or load balancer with a valid certificate, so traffic is encrypted and authenticated in transit.

Why it’s needed. To retrieve the software, to address the services by stable names, and to protect traffic — the same baseline as any internal web service.

You provide outbound access, DNS records, certificates. From IntentGate the registry token.

4Identity provider for sign-in (SSO)

What it is. IntentGate does not maintain its own user accounts or passwords for the console. It delegates authentication to your existing identity provider (IdP) over the OIDC standard — the same single sign-on your staff already use for email and other internal apps (Microsoft Entra ID, Okta, Google Workspace, and similar).

You register IntentGate as an application in your IdP once. That registration produces three values you enter into the configuration:

Issuer URL
the address of your IdP, e.g. https://login.your-company.com.
Client ID
the identifier your IdP assigns to the IntentGate application.
Client secret
the credential proving the request originates from IntentGate.
Why it’s needed. So console access is limited to your employees, using credentials they already hold, with no separate user directory or passwords for IntentGate to store.

You provide the IdP application registration and the three values (IT / identity team).

Additional, depending on scale

Database. IntentGate stores policies, audit records, and inventory in PostgreSQL. For a pilot it is in the box — nothing to provision. For always-on production, point IntentGate at your own managed PostgreSQL with failover.

Workloads to protect. A tool / MCP server to place behind the gateway, and the agents that will call it — or a plan to onboard them. Starting with none is fine.

Local tooling. openssl (to generate secrets), curl, and a terminal on the machine you work from. Docker covers the rest.

Operating for resilience (high availability)

A single host is fine for a pilot. For production, companies remove the single point of failure so that one crash or restart never stops enforcement. Three changes make the platform highly available.

1 · Run several gateways behind a load balancer

Run two or more copies of the gateway and put a load balancer in front of them. If one fails, the others keep serving — the load balancer simply stops sending traffic to the failed one. The gateway holds no per-request state, so adding copies is safe and linear.

2 · Give the gateways a shared Redis

Budgets (spend and rate limits) are the one thing the gateways must agree on. Point every gateway at the same Redis by setting INTENTGATE_REDIS_URL on each one — the gateway then keeps its budget counters in Redis, so all copies count against one shared total. This is several checkpoints sharing a single tally board rather than each keeping its own. Without Redis, each copy counts separately and a limit is effectively multiplied by the number of copies — which is why Redis becomes required the moment you run more than one gateway.

3 · Use managed PostgreSQL

Move policies, audit, and inventory onto your own managed PostgreSQL with failover, rather than the bundled single instance. Note that enforcement does not depend on the database at request time — policy is held in memory and audit is streamed — so a database interruption degrades management and reporting, not protection.

The console stays a single instance; it sits off the traffic path, so if it restarts, agents keep calling and the gateways keep enforcing — you simply can’t manage settings until it returns.

In short. Several gateways + a load balancer + shared Redis + managed PostgreSQL gives you a platform with no single point of failure on the enforcement path. The ready-to-run docker-compose.ha.yml in this folder wires Redis, two gateway replicas, and a load balancer; for Kubernetes, use the Helm chart.

You provide the load balancer (or use the bundled one), a Redis endpoint, and managed PostgreSQL. In the box the Redis wiring and replica configuration.

Checklists

Complete these before install day. When all five are satisfied, the host is ready for the three install commands in README.md.

A · Host

  • Linux host (~4 vCPU / 8 GB RAM / 20 GB disk for a pilot)
  • Docker Engine and Docker Compose v2 installed
  • openssl and curl available on your working machine

B · Network & segmentation ★ most important

  • Agents can reach the host on port 8080
  • The host can reach the tool / MCP server
  • Firewall rule: tool server accepts traffic only from the gateway — prevents agents bypassing IntentGate
  • Outbound access to ghcr.io (or an internal mirror)
  • Internal DNS records for the gateway and console
  • TLS certificate and reverse proxy / load balancer for the console

C · Identity (SSO)

  • IntentGate registered as an OIDC application in your IdP
  • Redirect URL set to the console address
  • Issuer URL, Client ID, and Client secret recorded

D · From IntentGate

  • License key
  • Registry token for image pulls
  • Release version to pin (e.g. 1.6.2)

E · Workloads & scale

  • A tool / MCP server to place behind the gateway
  • Agents that will use it — or a plan to onboard them
  • Production: managed PostgreSQL with failover
  • Multiple gateway replicas: a Redis endpoint
